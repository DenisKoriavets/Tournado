# ADR-0004: Persistence - PostgreSQL + Spring Data JPA + Flyway

- **Status:** Accepted
- **Date:** 2026-10-27

## Context

The domain is strongly relational: users ↔ teams ↔ roster members ↔ registrations ↔ tournaments ↔ bracket ↔ matches ↔ score submissions ↔ disputes (digest §1). Many rules are uniqueness or counting constraints that must hold under concurrent requests: unique team name per discipline (BR-06), no duplicate registration (BR-21), slot limit never exceeded (BR-20, NFR-05), one active dispute per match (BR-45), a team advances at most once (NFR-09). Results are immutable after completion (BR-52), and roster identifiers are snapshotted at lock (ASM-09). Disputes include an uploaded screenshot (US-30).

## Decision drivers

- Relational data with many joins (bracket, rosters, standings, CSV).
- Uniqueness and concurrency guarantees enforced by the database, not only by code (NFR-05, NFR-06, NFR-08).
- Repeatable schema on every laptop (one-command startup).
- Free, local, familiar to the team.
- Deadlines and timers stored durably (ADR-0005).

## Considered options

**Database**

| Option | Pros | Cons |
| :--- | :--- | :--- |
| **A. PostgreSQL** | Relational, ACID, unique / check / foreign-key constraints, row locks (`SELECT … FOR UPDATE`), `timestamptz`, free, runs in Docker | Needs a running server (solved by Docker Compose) |
| B. MongoDB | Flexible documents | Relations (team ↔ tournament ↔ match) become manual references; multi-document invariants are harder; weaker fit for bracket/standings queries |
| C. SQLite / H2 file | Zero setup | Weak concurrent writes (SQLite locks the whole DB); H2 behaves differently from production databases; not suitable for scheduled jobs + WebSocket writes at the same time |

**Data access**

| Option | Pros | Cons |
| :--- | :--- | :--- |
| **A. Spring Data JPA (Hibernate)** | Familiar, fast CRUD, optimistic locking with `@Version`, works with Spring transactions | Hidden queries (N+1), lazy-loading pitfalls |
| B. jOOQ / JdbcTemplate | Explicit SQL, full control | More boilerplate for 4 developers |

**Schema management**

| Option | Pros | Cons |
| :--- | :--- | :--- |
| **A. Flyway SQL migrations** | Versioned plain SQL in Git, applied automatically on startup, same schema everywhere | Must write SQL by hand |
| B. Hibernate `ddl-auto=update` | No migration files | Non-deterministic, cannot express all constraints, dangerous with shared data |
| C. Liquibase | Powerful | XML/YAML changelogs are heavier than plain SQL for a student team |

## Decision

- **PostgreSQL** (official Docker image) as the single source of truth.
- **Spring Data JPA** for regular access; native SQL or `@Query` allowed where JPA is awkward (standings, bracket queries, row locks).
- **Flyway** migrations in `core/src/main/resources/db/migration` (`V1__init.sql`, `V2__…`). `ddl-auto` is `validate`, never `update`.

Conventions the technical contracts must follow:

| Topic | Convention | Reason |
| :--- | :--- | :--- |
| Primary keys | `UUID`, generated by the application | Public links must not be guessable or sequential (BR-15); IDs can be created before insert |
| Time | All instants stored as `timestamptz` in UTC; Java `Instant`; the client shows local time | Deadlines are compared on the server (NFR-07, ASM-15) |
| Invariants | Enforced with DB constraints: `UNIQUE`, `CHECK`, `FOREIGN KEY`, partial unique index for "one active dispute per match" | Holds under concurrency even if code has a bug (NFR-05, NFR-06) |
| Concurrency | `@Version` optimistic locking on aggregates that change state (tournament, match); `SELECT … FOR UPDATE` for the last-slot registration | NFR-05, NFR-08 |
| Enumerations | Stored as `text` with `CHECK` constraints, mapped to Java enums | Readable in SQL, safe to extend |
| Snapshots | Roster identifiers copied into tournament-registration rows at lock | ASM-09, NFR-11 |
| Screenshots | Saved as files on a Docker volume (`/data/uploads`); only metadata and path in the DB | Keeps the DB small; no paid object storage |
| Audit | Decisions (dispute closure, technical loss, exclusion, removal) store who/what and when | ASM-26, NFR-26 |

## Consequences

**Positive**
- The database itself guarantees the key business invariants.
- Every developer gets an identical schema with `docker compose up`.

**Negative**
- Hand-written SQL migrations; a broken migration blocks startup for everyone (mitigation: never edit an applied migration, always add a new one).
- JPA performance pitfalls must be watched in bracket/standings queries.

**Risks**
- Local file storage for screenshots is lost if the volume is deleted. Acceptable for a local MVP.

**When to revisit**
- Object storage (S3 / MinIO) only if the app is deployed to more than one machine.
