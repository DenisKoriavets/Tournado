# Prompt 6.3: QA Audit of Test Coverage & Bug Diagnosis

## Role & Context
The AI generated the tests (prompt 6.2), and they all passed. "All green" is not proof of quality, so a separate **read-only** AI agent, with no write access and no stake in the tests passing, audited them against the Gherkin requirements and looked for fake tests and real product bugs.

- **Agent definition:** [`.claude/agents/qa-auditor.md`](../.claude/agents/qa-auditor.md) (tools: Read, Grep, Glob, Bash; edits forbidden)
- **Results and our responses:** [`docs/testing-report.md`](../docs/testing-report.md) §3 and §5

---

## 1. Audit prompt (sent to the `qa-auditor` agent)

```markdown
Audit the stories covered by new tests in this branch against docs/requirements.md §5 (Gherkin + checklist):
US-12, US-05 (+ US-14 sc.2/sc.3), US-27, US-28 (backend API integration tests in
core/src/test/java/com/tournado/core/*/integration/*IntegrationTest.java, base class .../support/),
and the frontend component tests for US-05, US-08, US-11, US-27, US-30, US-31, US-32, US-33, US-34
in frontend/src/**/*.test.ts(x).

Follow your instructions exactly:
- a coverage table per scenario and checklist item;
- gaps, especially negative and boundary cases;
- anti-patterns: self-testing mocks, status-only assertions, order dependence, sleeps, CLAUDE.md §6 style violations;
- suspected product bugs where code and requirement disagree, with file:line.
Also check that the rules in docs/testing-strategy.md are actually followed (file per story, naming, DB isolation via TRUNCATE).
You may run `npx vitest run`. Do not edit any files.
Output: table + top-5 prioritized actions + suspected bugs, under ~900 words.
```

## 2. Bug diagnosis prompt (applied to each suspected bug before changing anything)

```markdown
The QA audit claims: "<claim with file:line>".
Before changing code, verify it against the sources of truth and answer in 3 lines:
1) What do docs/requirements.md (story checklist/Gherkin) and docs/contracts/* say exactly? Quote the line.
2) What does the code do (file:line)? Is there an existing test that locks the current behaviour?
3) Verdict:
   - BUG (code violates both requirement and contract) → fix the code and write a test that is red on the old code;
   - DOC DRIFT (requirement and contract disagree; the code follows the contract) → do not change code, record it;
   - BY DESIGN → record the reason.
Never change a test's expected value to match the code unless the requirement or contract says the code is right.
```
