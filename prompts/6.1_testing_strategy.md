# Prompt 6.1: Architecture Analysis & Testing Strategy

## Role & Context
Act as a Senior QA Architect joining the Tournado monorepo (Spring Boot 3 core + React 19/TypeScript frontend + FastAPI ai-service + PostgreSQL 16) right after the MVP vertical slices were merged into `main`. The goal is a short, project-specific `docs/testing-strategy.md` that the team and AI agents will follow when writing tests. It must not be a generic QA textbook.

**Output:** [`docs/testing-strategy.md`](../docs/testing-strategy.md)

---

## Prompt

```markdown
You are a Senior QA Architect. Analyse this repository and write `docs/testing-strategy.md`: 1–2 pages, concrete, no theory.

STEP 1: Inventory (read-only, report facts before writing anything):
- Read CLAUDE.md, AGENTS.md, docs/adr/*, docs/contracts/*, and the "Acceptance Criteria" section of docs/requirements.md.
- For core/, frontend/ and ai-service/, list:
  - every existing test file and how many tests it has;
  - the test type (unit / @WebMvcTest / integration);
  - what is mocked;
  - whether any test touches a real database;
  - how test data is created and cleaned up.
- List the controllers and endpoints on `main`, and the backend features that have no UI.
- Check the tooling: Maven / Maven Wrapper, Node, Python, Docker, CI, and whether a single command runs all tests.

STEP 2: Decide, and justify each decision in one sentence:
- Which test level is the main one for this client-server system? Prefer the cheapest level that still catches the bug. Business rules, persistence and HTTP error codes must be tested through the real HTTP + DB chain.
- How to run PostgreSQL in tests. Migrations use `uuid-ossp`, `TIMESTAMPTZ` and CHECK constraints, so an H2 substitute is NOT acceptable.
- What is automated (Bucket 1) and what stays on a manual smoke checklist (Bucket 2): layout, real OAuth/Steam, live WebSocket UX, real LLM calls.

STEP 3: Write the document with exactly these sections:
1. Goal and the main rule: tests come from Gherkin requirements, never from reading the implementation.
2. Scope In / Scope Out: a two-column table specific to Tournado.
3. Test levels and tools: a table with level, folder, libraries, purpose.
4. File organization and naming:
   - one file per user story;
   - one Gherkin scenario = one test;
   - Java naming `givenX_action_shouldZ` from CLAUDE.md plus `@DisplayName("US-xx sc.N: ...")`;
   - AssertJ recursive comparison, and errors asserted as status + RFC 7807 `code`.
5. Test data and isolation: where data comes from, how the DB is reset before each test, how users are authenticated, and why no test depends on the seed migrations.
6. Quality gate:
   - the exact commands that must be green before merging into `main`, including ONE root command that runs all suites;
   - the 3 acceptance checks for AI-generated tests: mutation check, no self-testing mocks, run twice.
7. Known risks: 2–3 real technical risks found in the code, each with its current mitigation.

CONSTRAINTS:
- Use only tools that fit the existing stack (JUnit 5, Spring Boot Test, MockMvc, AssertJ, Mockito, Vitest, Testing Library, pytest). Name versions only where they matter for compatibility.
- Every rule must be checkable in the repository: a path, a class name, a command.
- Do not invent endpoints, error codes or fields. Take them from docs/contracts/.
- English, Markdown. At most ~120 lines.
```

## Follow-up prompts used during the session

1. *"Docker Desktop on this machine crashes on stale AF_UNIX socket files. Analyse what is wrong before changing the approach."*
   - The analysis found low free space on C:, and the Docker data dir is on D:.
   - We first switched to embedded PostgreSQL, then returned to **Testcontainers** after Docker was fixed, because the team chose Docker as the single runtime.
2. *"Testcontainers 1.19 (Spring Boot 3.3 BOM) cannot talk to Docker Engine 29."* The fix was to pin `testcontainers.version` to 1.21.4 in `core/pom.xml`.

## What we changed in the AI output
- The AI listed H2 as a "no Docker" alternative for the DB. We ruled it out ourselves because the migrations use `uuid-ossp`, `TIMESTAMPTZ` and CHECK constraints, and an H2 run would test a different database than production.
- When Docker failed, the AI's first move was to retry starting Docker in a loop. We stopped it and asked for a root-cause analysis instead. The cause was stale socket files plus a nearly full C: drive (the Docker data dir is on D:).
- The AI's first draft required `-DargLine="-Dnet.bytebuddy.experimental=true"` on every Maven call (inherited from the README). We moved it into the `maven-surefire-plugin` config so `mvnw test` and `npm test` work without extra flags.
- We kept the existing `@WebMvcTest` and Mockito tests and did NOT ask the AI to rewrite them. The new strategy adds the missing level (real HTTP + real PostgreSQL) instead of duplicating what exists.
