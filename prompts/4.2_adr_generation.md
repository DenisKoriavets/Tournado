# Prompt 4.2: Architecture Decision Records (ADR)

## Role
Act as a pragmatic Software Architect who has shipped several student and early-stage startup projects. You prefer boring, well-known technology, you count every extra moving part as a cost, and you justify every decision by the team's real constraints, not by industry fashion.

## Context
We are building **Tournado**, a web platform for organizing amateur and student esports tournaments (Counter-Strike 2 5v5, Brawl Stars 3v3, Chess.com 1v1). The MVP scope, user stories and acceptance criteria are in `docs/requirements.md`. The requirements analysis (entities, lifecycles, business rules BR-xx, non-functional requirements NFR-xx, gaps GAP-xx and assumptions ASM-xx) is in `docs/analysis/requirements-digest.md`. Read both before answering.

Key technical drivers from the MVP:
- Real-time Match Room: Ready Check with a 10-minute timer, alternating map bans with a 30-second turn timer; both captains must see the same state.
- Many time-based automatic transitions (roster lock, check-in open/close, exclusion, bracket generation, technical loss, ban timeout, Chess.com polling) that must fire without any user online; the server clock is authoritative (NFR-07, NFR-13).
- Concurrency-sensitive rules: last free slot, duplicate registration/check-in/ready, simultaneous score submissions (NFR-05, NFR-06, NFR-08).
- AI dispute assistant: reads a scoreboard screenshot, returns score + nicknames + confidence; advisory only, a failure must degrade to "not recognised" (NFR-19, NFR-20, NFR-22).
- External integrations: Steam login, Chess.com public read-only API.

## Team constraints (hard)
- 5 students, one semester; the MVP must be demoed live at the end of the course.
- Roles: Core Platform & Auth, Tournament Engine, Game Integrations & Match Flow, AI & Automation, Frontend.
- Budget: 0. No paid hosting, no paid APIs. Everything runs locally on the students' laptops.
- The project must start locally with 1-2 commands.
- Team decision already made by vote: core backend in **Java (Spring Boot)**, AI module in **Python**. The frontend owner chose **React + TypeScript + Vite**. All members are roughly familiar with these stacks.

## Initial architecture sketch from the team (to be challenged)
```
Web client  --HTTP/WebSocket-->  Core service (Java 21 / Spring Boot 3: auth + RBAC, tournament engine, STOMP gateway)
Core  --JDBC-->  PostgreSQL 16
Core  --Redis protocol-->  Redis 7 (Match Room state, pick/ban timers, task queue via Streams)
Redis queue  -->  AI worker (Python 3.12 / FastAPI: Vision dispute analysis, rules generation)
```

## Task
Produce a set of ADRs covering the key nodes of the system:
1. Overall repository structure (monorepo vs separate repositories, folder layout).
2. UI stack.
3. Backend / business logic stack and its internal structure.
4. Data persistence (relational vs document DB, ORM, migrations, time and ID conventions, file storage for screenshots).
5. Real-time communication and server-side timers.
6. AI module: service boundary, communication with the core, model provider under a zero budget, failure handling.
7. Authentication and session handling (Steam login + e-mail login).
8. External game integrations for the MVP (what we integrate with and what we deliberately do not).
9. Local development and one-command startup.

For **every** ADR:
- Compare at least 2-3 realistic alternatives against explicit decision drivers taken from the constraints and from the digest (cite BR/NFR/GAP/ASM IDs).
- Critically evaluate the team's sketch. If a component (for example Redis or a message queue) is not justified at MVP scale, say so, propose the simpler option, and state under which future conditions the rejected option would become necessary.
- Record the consequences honestly: what we gain, what we pay, and the risks.
- Do not invent requirements and do not expand the MVP scope (rules generation by AI is Post-MVP).
- Do not design the database schema or the API endpoints - that is the next step (technical contracts). Only fix the conventions those contracts must follow.

## Output format
- One file per decision: `docs/adr/NNNN-short-title.md`, using the structure: Status, Date, Context, Decision drivers, Considered options (table with pros/cons), Decision, Consequences (positive / negative / risks), Related.
- An index `docs/adr/README.md` with the team constraints and a table of all ADRs with one-line summaries.
- Write in English, concise and specific. Prefer tables over long prose.
