# Prompt 6.2: Requirement-Driven Test Generation

## Role & Context
Generate API integration tests for the key MVP user stories from their **Gherkin acceptance criteria** (`docs/requirements.md` §5). The AI must not read the implementation to decide what is "correct". The instructions are packaged as a reusable Claude Code skill so every story is generated the same way.

- **Skill:** [`.claude/skills/generate-tests/SKILL.md`](../.claude/skills/generate-tests/SKILL.md) (full text in the repository)
- **Rules it follows:** [`docs/testing-strategy.md`](../docs/testing-strategy.md)
- **Result:**
  - `core/src/test/java/com/tournado/core/support/` (`IntegrationTestBase`, `DbFixtures`, `ApiError`)
  - 3 test classes, 31 tests on the first pass. After the QA audit (prompt 6.3) there are 5 classes and 44 tests (+US-34, +US-08).

---

## 1. Infrastructure prompt (run once)

```markdown
Following docs/testing-strategy.md §3 and §5, create the shared infrastructure for API integration tests in core:
- `IntegrationTestBase`:
  - `@SpringBootTest` + `@AutoConfigureMockMvc`;
  - ONE `postgres:16-alpine` Testcontainers container per JVM (singleton, `@ServiceConnection`), not one per class, because Spring caches the context;
  - `@BeforeEach` that TRUNCATEs every table except `flyway_schema_history` (CASCADE);
  - helper `bearer(userId)` that signs a real JWT with `JwtTokenService`;
  - helpers `json()`, `read()`, `readError()`.
- `DbFixtures`: plain-SQL builders for the "Given" state only (players with or without game identifiers, teams / full teams, invites, tournaments with an arbitrary deadline and status, registrations, brackets and matches). Respect every CHECK and FK constraint of V1__initial_schema.sql.
- `ApiError(int status, String code)`: the stable part of RFC 7807 that tests compare.
Add the test dependencies to core/pom.xml. Do NOT add H2.
```

## 2. Generation prompt (per story)

In this iteration the backend tests were generated in a Claude Code session with the prompt below, one story at a time. The same procedure was then packaged as the `generate-tests` skill, so the next stories (including the new frontend screens) are generated with `/generate-tests US-xx core|frontend`.

```markdown
Write API integration tests for user story US-12 (then US-05, then US-27 + US-28).
Source of truth: the "### US-12" section of docs/requirements.md §5 (checklist + Gherkin "Дано/Коли/Тоді"),
error codes in docs/contracts/error-format.md, rules in docs/testing-strategy.md.
Use the implementation ONLY to find the endpoint path and DTO names. Never take expected behaviour from the code.
- One Gherkin scenario = one test: `givenX_action_shouldZ` + `@DisplayName("US-12 sc.N: ...")`.
  Checklist items without a scenario become `US-12 checklist: ...` tests.
- Extend IntegrationTestBase. Insert only the "Given" state with DbFixtures. "When" is a real HTTP call with a real JWT.
- Assert: HTTP status, the response DTO via recursive comparison, errors as ApiError(status, code),
  and the DB state afterwards (no row created on rejection).
- Happy path + every negative/boundary case (401/403/409/422, last free slot, duplicate, deadline just passed).
First print a table "Scenario | Test | Expected" for approval, then write the file
core/src/test/java/com/tournado/core/<module>/integration/<Feature>IntegrationTest.java and run it.
If a test fails because the app violates the requirement, STOP and report the bug. Do not weaken the test.
```

| sc.6 Last slot (15/16) | `givenOneFreeSlotLeft_register_shouldAcceptLastTeamAndRejectNext` | 201 for the 16th team, 409 for the 17th |
| checklist | missing Steam ID / other discipline / non-captain / anonymous | 422 `MISSING_GAME_IDENTIFIER` / 422 / 403 / 401 |

## 3b. Frontend: component tests for the new MVP screens

The same rules (skill `generate-tests`, mode `frontend`) were applied to the new UI from the validated plan [`docs/superpowers/plans/2026-11-26-frontend-mvp-ui-practice-6.md`](../docs/superpowers/plans/2026-11-26-frontend-mvp-ui-practice-6.md):

```markdown
Write Vitest + Testing Library component tests for US-27, US-30, US-31, US-32, US-33, US-34 (then US-05, US-08, US-11).
Source of truth: docs/requirements.md §5 (Gherkin + checklist) and contract shapes in docs/contracts/api-contracts.md Epic 7–8.
- One scenario = one `it('US-xx sc.N: ...')`. Checklist items: `it('US-xx checklist N: ...')`.
- Replace HTTP ONLY at the src/api/* boundary with vi.spyOn. Never mock the component or the validator under test.
- Assert what the user sees: text, enabled or disabled controls, aria-invalid. Assert the exact API call arguments.
  Assert that no API call is made when client validation must block the action.
- Use contract-shaped fixtures (confidence is 0..1 → shown as %). No snapshots, no real sleeps:
  polling is tested with vi.useFakeTimers({ shouldAdvanceTime: true }) + act(() => vi.advanceTimersByTimeAsync(ms)).
- If a test fails because the component violates the scenario, fix the component and report it. Do not weaken the test.
```

## 4. Corrections we made to the AI output
- The first version of the US-12 happy path compared the registrations list field by field (`extracting("teamId", "teamName", ...)`). That breaks the CLAUDE.md §6 rule, so it was replaced with a recursive comparison against an expected `TournamentRegistrationsResponse`.
- The first `IntegrationTestBase` used `@Testcontainers` + `@Container` on a static field in an abstract class. That lifecycle stops the container after the first test class while Spring keeps the cached context with the old port, so it was replaced with a JVM-wide singleton container.
- A frontend assertion looked for `13:9` anywhere on the dispute card and would have passed without the AI hint, because the captains' scores also contain `13:9`. It is now scoped with `within()` to the «Підказка ШІ» block.
- When the score test failed on `13.5`, we fixed the application (`spring.jackson.deserialization.accept-float-as-int: false`) instead of deleting that case from the test.
